# Спецификация: раздел «Статьи» (зеркало «Охватории») + страница «Кит_Биржа»

Дата: 2026-06-27
Проект: сайт 24kitbot.ru (Astro, `site/`)

## Цель

Две новые фичи по заказу клиента, обе с автоматическим обновлением:

1. **Раздел «Статьи»** — посты из MAX-группы «Охватория. Админам от админов»
   (`max.ru/se13299904_biz`) автоматически появляются на сайте как статьи, с картинками.
2. **Страница «Кит_Биржа»** — каталог всех каналов, которые когда-либо участвовали
   в розыгрышах: название, кликабельная ссылка, число подписчиков; с сортировкой
   по числу подписчиков.

## Контекст и ограничения

- Сайт **статический** (Astro → GitHub Pages, домен 24kitbot.ru). Контент должен
  попадать в HTML на этапе **сборки** (ради SEO/AEO — это главный смысл сайта).
- Данные живут на **боевом VPS**: БД бота `raffle.db` (каналы, подписчики) и токен
  MAX (чтение постов «Охватории» через `getMessages`).
- Туннель бота (cloudflared quick-tunnel) **нестабилен** — адрес меняется, поэтому
  забирать данные «снаружи» (GitHub Actions → бот) ненадёжно. Данные должен
  **выталкивать** сам VPS (push-модель).
- **Боевой бот нельзя дестабилизировать.** Сборка сайта не должна крутиться внутри
  процесса бота и желательно вообще не на сервере бота.
- Локальная сборка Astro работает (CSS вынесен в `public/styles.css`, мимо бандлера).
- gh-токен сейчас **без scope `workflow`** → GitHub Actions деплой не настроен.

## Архитектура (вариант A — утверждён клиентом)

```
[VPS, крон]  generate-site-data.mjs (отдельный процесс, НЕ трогает бота)
   ├─ читает raffle.db (read-only)         → channels.json
   ├─ getMessages(Охватория) через MAX API → articles/*.md + public/articles/*.jpg
   └─ git commit + push в main репозитория сайта
                         │
                         ▼
[GitHub Actions]  on: push main (+ cron-расписание для подстраховки)
   └─ npm ci → astro build → deploy на gh-pages
                         │
                         ▼
              GitHub Pages → 24kitbot.ru
```

Принципы:
- **Генератор данных** и **сборщик сайта** разделены. Генератор — на VPS (там данные),
  сборщик — в GitHub Actions (подальше от боевого бота, бесплатно, с логами/повторами).
- Генератор **идемпотентен**: повторный прогон добавляет только новое, ничего не ломает.
- Если генератор падает (нет новых данных / ошибка MAX) — он просто ничего не коммитит,
  сайт остаётся в прошлом валидном состоянии.

### Разовая настройка (вне кода, делается с участием клиента)
- Клиент один раз выдаёт токену права `workflow` (`gh auth refresh -h github.com -s workflow`),
  чтобы залить `.github/workflows/deploy.yml`.
- На VPS — учётка для пуша в репозиторий сайта (deploy key или PAT, repo scope) +
  клон репозитория сайта.
- Крон на VPS (например, раз в час или раз в день) запускает генератор.

## Компонент 1: генератор данных (VPS)

Файл: `site/scripts/generate-site-data.mjs` (запускается на VPS; использует токен бота
из окружения сервера и путь к боевой `raffle.db`).

### 1a. channels.json (для «Кит_Биржи»)
- Собрать **все** каналы, замеченные в розыгрышах за всё время. Источники в БД:
  `raffles.sponsors`, `raffle_publications.channel_id`, `raffle_partner_requests.channels`,
  `user_channels`. Объединить по `channel_id` (uniq).
- Для каждого канала:
  - `title` — последнее известное название (`channel_link_state.title` →
    fallback `user_channels.channel_title` → `getChatInfo`).
  - `link` — последняя известная ссылка (`channel_link_state.link` → `getChatInfo`).
  - `subscribers` — последний снимок из `channel_subscribers_history`
    (max `recorded_at`) → fallback живой `getChatInfo().participants_count`.
- Отфильтровать мусор: без названия/ссылки — пропускать; удалённые каналы — пропускать.
- Записать в `site/src/data/channels.json`: массив
  `{ title, link, subscribers, channelId }`, отсортированный по `subscribers` убыв.
- Поле `generatedAt` (ISO) — для отметки «обновлено …» на странице.

### 1b. articles (для раздела «Статьи»)
- `getMessages(OHVATORIA_CHAT_ID, count=N)` — прочитать последние N постов группы.
  `chat_id` группы определить на этапе реализации (бот уже в группе).
- Для каждого поста:
  - Стабильный `id` = `message_id` (или mid) → имя файла `articles/<id>.md`. Если файл
    уже есть — **пропустить** (идемпотентность).
  - `title` — первая непустая строка/предложение поста (обрезать до ~90 симв.).
  - `description` — первые ~160 символов текста (для SEO/OG/превью).
  - `pubDate` — время поста (timestamp из MAX).
  - Текст: конвертировать форматирование MAX (жирный, заголовки, ссылки) в Markdown.
    Сохранить жирный/заголовки/списки («как у нас»).
  - Картинки: для каждого image-вложения скачать файл в `public/articles/<id>-<n>.jpg`;
    первую сделать «обложкой» (`image` в frontmatter), остальные вставить в тело.
    **Скачиваем к себе**, не горячая ссылка на MAX (надёжность + SEO).
  - Посты без текста (только стикер/реакция) — пропускать.
- Записать `site/src/content/articles/<id>.md` с frontmatter:
  `title, description, pubDate, image (опц.), sourceUrl (ссылка на пост в MAX, опц.)`.

## Компонент 2: страницы и навигация (Astro)

### 2a. Коллекция `articles`
- В `src/content.config.ts` добавить коллекцию `articles` (glob по
  `src/content/articles/*.md`), schema: `title, description, pubDate, image?, sourceUrl?`.
- `src/pages/articles/index.astro` — список статей (новые сверху), карточки с обложкой,
  заголовком, описанием.
- `src/pages/articles/[...slug].astro` — страница статьи (рендер Markdown + обложка),
  JSON-LD `BlogPosting` + breadcrumbs (по образцу текущего `/blog`).
- Переиспользовать `BlogLayout` (или его стиль). Не дублировать без нужды.

### 2b. Страница «Кит_Биржа»
- `src/pages/birzha.astro` — читает `src/data/channels.json` на этапе сборки.
- Таблица, колонки: **Канал** (название + ссылка `target=_blank rel="nofollow noopener"`)
  и **Подписчиков** (число, формат «12 345»).
- Сортировка: по умолчанию по подписчикам убыв. (уже отсортировано в JSON). Клик по
  заголовку колонки — пересортировка на клиенте (небольшой inline-скрипт; таблица уже
  в HTML ради SEO, JS только переставляет строки).
- Подпись «Обновлено: <дата>» из `generatedAt`.
- SEO: заголовок «Кит_Биржа — каталог каналов MAX», описание; опц. JSON-LD `ItemList`.

### 2c. Навигация
- В `src/data/site.ts` → `NAV` добавить пункты `{ /articles, 'Статьи' }` и
  `{ /birzha, 'Кит_Биржа' }`. Проверить, что шапка не переполняется на мобильном
  (сейчас 4 пункта, станет 6) — при необходимости ужать.

## Компонент 3: деплой (GitHub Actions)

- `.github/workflows/deploy.yml`: триггеры `push: branches [main]` + `schedule` (cron,
  подстраховка) + `workflow_dispatch` (ручной запуск). Шаги: checkout → setup-node 20 →
  `npm ci` → `npm run build` → `actions/upload-pages-artifact` + `actions/deploy-pages`
  (или `withastro/action@v3`). Pages переключить на источник «GitHub Actions».
- Требует разового `workflow` scope (см. «Разовая настройка»).

## Что НЕ делаем (YAGNI)
- Не делаем комментарии/лайки/поиск по статьям.
- Не делаем пагинацию (постов и каналов пока немного; добавим, если понадобится).
- Не делаем редактирование статей на сайте — сайт строго зеркалит «Охваторию».
- Не трогаем существующие страницы и дизайн-токены, кроме добавления 2 пунктов меню.

## Риски и проверки на этапе реализации
1. **chat_id «Охватории» и формат `getMessages`** — подтвердить, что бот реально читает
   посты и что в ответе есть текст + токены/ссылки картинок. (Бот уже в группе — клиент.)
2. **Скачивание картинок MAX** — проверить, что URL вложений публично доступны для
   загрузки скриптом.
3. **Доступ к VPS** (git, права пуша, путь к raffle.db, переменная токена) — проверить
   перед настройкой крона. Сервер трогаем только по явному «заливай».
4. **Шапка на мобильном** при 6 пунктах меню — проверить скриншотом.

## Критерии готовности
- `npm run build` собирает сайт с разделом `/articles` (хотя бы 1 тестовая статья из
  «Охватории») и страницей `/birzha` с таблицей каналов.
- Сортировка таблицы работает кликом по заголовку.
- Генератор идемпотентен (повторный прогон не плодит дубли).
- Пункты «Статьи» и «Кит_Биржа» есть в меню, страницы открываются.
